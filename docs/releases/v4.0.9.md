# v4.0.9 Pricing Correction, Display Layer and Ledger Identity Fixes

This release was prepared for the DeepSeek pricing change announced for 2026-09-14. The official pricing page no longer schedules that change, so `4.0.9` ships the corrected price rules together with three defects found while re-verifying the price path, the client display layers and the usage ledger, plus one silent-failure fix for the client settings write path that came from a community report.

## 1. Pricing: the 2026-09-14 V4 Pro change was withdrawn

Earlier official text said that from 2026-09-14 12:00 Beijing time `deepseek-v4-pro` requests would be billed at Flash rates. The current pricing page states the opposite in note (2): DeepSeek will keep serving the V4 Pro API after 2026-09-14 with the billing method unchanged, and will announce any change separately.

`4.0.8` carried a `PRO_ROUTED_PRICE_TABLE` and switched `deepseek-v4-pro` to Flash prices at that instant. With the change withdrawn, that switch would have priced every V4 Pro call after the boundary at Flash rates, undercounting the amount by roughly 73% relative to the published Pro prices. `4.0.9` removes the routed table and the `PRO_FLASH_PRICING_START` boundary. The built-in table version is now `2026-09-13` and the model list matches the page: `deepseek-flash` (DeepSeek-V4.1-Flash), `deepseek-v4-flash`, `deepseek-v4-flash-vision-exp` on Flash prices, and `deepseek-v4-pro` on Pro prices.

| Model group | Off-peak cache hit / miss / output | Peak cache hit / miss / output |
| --- | --- | --- |
| Flash series | ¥0.02 / ¥1 / ¥4 | ¥0.04 / ¥2 / ¥8 |
| `deepseek-v4-pro` | ¥0.15 / ¥4.5 / ¥13.5 | ¥0.30 / ¥9 / ¥27 |

Peak hours stay weekday 09:00-12:00 and 14:00-18:00 Beijing time, with weekends fully off-peak.

## 2. Host: the default price table skipped every historical price segment

`selectPriceTable()` decided whether it was looking at the built-in table with an object identity comparison, `table !== PRICE_TABLE`. The settings schema declares `priceTable` as `z.any().default(PRICE_TABLE)`, and schemastery returns a deep copy for a parsed default, so the comparison was always true and the table was always treated as a user-supplied override. A custom table is applied to all calls as a whole by design, so the official segments never ran:

- calls before 2026-08-17 00:00 Beijing time should use the pre-peak uniform price (`LEGACY_PRICE_TABLE`),
- calls between 2026-08-17 00:00 and 2026-09-10 12:00 Beijing time should use the pre-Flash peak/off-peak prices (`PRE_FLASH_PRICE_TABLE`),
- and both were billed with the current Flash table instead.

The projection cache made this reachable on any normal install: `createTokenCostProjectionDefinition(priceTable)` captured the table by value at registration, and the projection rebuild uses it to fold historical `llm.usage` events. Affected sessions therefore showed an amount that did not match the published prices.

`4.0.9` compares the table by content through `isOfficialPriceTable()` against `OFFICIAL_TABLE_SNAPSHOT`, so the schema-materialized default counts as the built-in table and the historical segments run. A genuinely custom `priceTable` keeps its documented behavior: it overrides the table as a whole and skips segmentation.

Two related changes come with it. `collector`, `tokenCost` projection and the budget routes now accept `PricingTable | (() => PricingTable)` and read the table through a live getter, because `ctx.inject` callbacks do not run inside the synchronous plugin body; a value captured there could be the pre-settings default. And the projection definition moves to `stateVersion: 6`, so cached rows written with the old amounts are discarded and recomputed from events on the next load. The `usage` ledger is never rewritten.

Reproduction: folding the 206 `llm.usage` events of a real affected profile gives ¥10.695487 with the fixed segmentation and ¥8.078978 with the identity check, an undercount of ¥2.616509 (24.5%). A projection-cache walk over five in-window sessions found two whose cached amount equalled the pre-fix fold result.

## 3. Client: the balance card and whale girl were painted under the right sidebar

The card is registered on `shell.overlay`, which the host renders inside `AppFrame.module.css`'s `.overlayLayer`. That element declares `z-index: 20`, so it creates a stacking context: the card's own `z-index: 1000` was only ever compared against siblings inside that layer. The right sidebar float host declares `z-index: 60` and is portalled to `document.body`, so it covered the whole card, whale girl included, regardless of the card's z-index value.

`4.0.9` portals the card to `document.body` and sets `CARD_Z_INDEX = 65`. The card is `position: fixed` and computes its geometry from `window.innerWidth`/`innerHeight` and `getBoundingClientRect()`, so the new mount point does not move it. The value is chosen against the host's own bands: `overlayLayer` 20, sidebar `floatHost` 60, dockkit menu 70, host overlays and menus at 100 and above, host modals and toasts at 1000 and above. 65 clears the sidebar float host while staying below the host's menus and modals.

## 4. Host: ledger identity for records without an event sequence

`UsageStorage` deduplicated only records that carry `sourceEventSeq`. Rows written before that field existed returned early from the duplicate check, so a repeat delivery of the same historical `assistant/message` was appended a second time and counted twice.

This path is real in the current host. `@deepseek-ai/dsh-session` documents that constructor seeds do not emit `session/event`, and `dsh-session-controller`'s `session/created` handler pushes the recorded seed suffix into the follower stream, which is a separate delivery path from the live event stream. A seed row that is also replayed reaches the collector twice.

`4.0.9` uses one identity function for both paths: `['seq', sessionId, sourceEventSeq]` when the sequence is known, otherwise a content tuple of session, turn, step, timestamp, provider, model, the five token counters and the five cost fields. `loadHistory()` and `add()` share one identity set, so the first accepted row wins and later identical rows are dropped. `costCache` and `peak` are deliberately excluded from the tuple: `normalizeUsageRecord` fills `costCacheRead` from `costCache` on historical rows, so including them would stop pre-existing rows from matching rows written after the upgrade.

The full `timestamp` is part of the tuple rather than a second-resolution value, so two genuinely distinct calls are never merged.

Replaying the real 533-row ledger through the new identity accepts 533 of 533 rows with 0 duplicates and a total of ¥19.537413, identical to the unfiltered sum. 521 of those rows carry no sequence, so the conservative tuple is exercised on real data without dropping anything.

## 5. Client: the whale girl toggle gave no visible feedback when the write failed

After PR #17 routed the toggle through the Host settings patch, `toggleWhaleGirl` still ended with `.catch(() => {})`. When the PATCH was rejected or the request failed, the click did nothing at all: the checkbox kept the new value locally, the Host kept the old one, and the user had no way to tell.

The error alone cannot distinguish "the Host did not persist the change" from "the Host persisted it but the response was lost", so `4.0.9` re-reads the authoritative snapshot through `settingsApi.get()` on failure, reconciles the checkbox with it, and shows a notice under the card. If the re-read fails too, the card keeps its current value instead of inventing a local one, and the notice asks the user to retry. The notice is an absolutely positioned sibling that hides itself after four seconds, so it does not change the card size or geometry and leaves the whale girl rendering contract untouched.

New test: the settings host double answers PATCH with `503 UNAVAILABLE`; the notice appears, the checkbox returns to the Host value, and the Host state stays unmodified.

## Contributions

`@gurio-wine` contributed two client fixes through PR #17 that are included here: the drag position is now stored as a separate user intent rather than the viewport-clamped render position, so minimizing or shrinking the window no longer persists a top-edge position, and the whale girl toggle writes through the Host settings patch instead of `localStorage`, so the unchecked state survives the focus refresh that previously restored the checkbox.
